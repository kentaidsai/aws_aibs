01

提案－解釋－驗證三步驟

Propose-Explain-Validate

Design 階段的核心節奏：先提出對應痛點的 AI capability，再用業務語言解釋對團隊的改變，最後拋出驗證問題確認 stakeholder 真正理解風險與控制，而不是只說「聽起來不錯」。

批次轉錄對應 2% call coverage 的痛點，提升為 100% 可搜尋逐字稿
🎯
02

痛點驅動能力，不可逆向

Pain Point Drives Capability

每一項 AI capability 都必須回溯到 Discover 階段診斷出的具體痛點，絕不能是技術驅動或投機性提案，否則就是本末倒置。

coverage gap、coaching lag、compliance risk、transcription burden 四項痛點各對應一項候選能力
🏗️
03

Build-Buy-Blueprint 決策

Build vs Buy vs Blueprint

傳統 build-buy-partner 框架少了「採用開源參考架構並客製化」這個選項；面對沒有 AI 經驗、8 週時程、prove-ROI-first 預算的團隊，blueprint 勝過從零建置或採購商業方案。

AWS PCA（Post Call Analytics）透過 CloudFormation 部署，無授權費，成本隨用量線性增減
🛡️
04

Governance by Design 三步驟

Identify-Propose-Validate

在架構鎖定前就把風險識別、具體控制措施提案、與 stakeholder 驗證內建進設計流程，而不是等架構定案後再補救，成本差異巨大。

PII 風險 → Amazon Transcribe 內建 redaction → 向合規負責人 Taylor 驗證是否足夠
⚖️
05

分層存取化解利害衝突

Tiered Access Resolves Conflict

QA 需要未遮蔽逐字稿做教練，合規要求全面遮蔽 PII；用分層存取（預設遮蔽、具名人員限時閱覽、全程稽核）同時滿足兩邊需求，而不是各退一步的妥協。

雙 S3 bucket + Cognito 權限分組 + CloudWatch 稽核 + 72 小時 lifecycle 自動到期
🌐
06

資料落地決定模型選擇

Data Residency Gates Model Choice

挑選摘要模型時，首要準則是資料是否離開 AWS 環境，其次才比較維運複雜度；策略顧問要攤開所有選項讓合規把關，而非自行先行篩選。

Bedrock（Claude）留在 AWS、低複雜度 → 建議採用；Anthropic API 直連因資料外流被合規否決
📊
07

風險等級對應新內容生成量

Risk Scales with Generated Content

處理既有資料的能力風險較低，產生全新內容的能力風險最高；風險等級直接決定治理控制的嚴謹程度與部署的先後階段。

轉錄／分類判定為低風險（Phase 1）；摘要判定為高風險，須逐一連結原始逐字稿並延後到 Phase 2
👥
08

治理角色具名分工

Named Governance Ownership

核准、實作、驗證、仲裁四項治理職責分別指派給具名的人，避免責任模糊；沒有具名擁有者的治理只是文件，不是真正的控制。

Taylor 核准、Jordan 實作 IAM/Cognito/S3、Riley 驗證輸出、Casey 仲裁取捨
📋
09

POC Scope Document 一文兩半

One Document, Two Halves

同一份文件分成兩半：POC scope（範圍、排除項、技術選擇、門檻）供工程團隊建置依據；pilot success criteria（基線、KPI、ROI、成本控制）供日後評估成效。沒有範圍工程會盲建，沒有準則沒人能證明價值。

範圍鎖定在 auto claims 單一險種，搭配 3-5 位資深 QA 分析師作為校準群組
📐
10

單一業務線換取乾淨訊號

Single Line of Business = Clean Signal

把 POC 限制在單一業務線而非跨險種整體平均，能孤立變因，讓改善與退步都清楚可見；每一項排除都要寫進文件，避免日後被悄悄加料。

Auto claims 納入範圍，Casualty／commercial 明確排除；即時 agent assist 延到 Phase 2+ 再談
📈
11

基線先行，KPI 對照業務成果

Baselines Before KPIs

試點啟動前先量測現況基線（coverage、coaching lag、compliance detection、每通成本），每項 KPI 都要對照同一基線，才能證明 AI 訊號真正轉化為業務成果，而不是事後重建數字。

Coverage 由 3% 目標提升到 100%；Analyst agreement 目標 95%；成本約 $0.12／call（試點）降至 $0.08／call（量產）
🔁
12

領先指標與人機協同校準

Leading Indicators & HITL

分析師覆寫率是最早的成敗訊號，但要追蹤覆寫的原因，而不只是數字本身；低信心輸出交由人工審查，審查結果回饋成為下一輪校準的 ground truth。

「分數錯了」代表模型問題要修 prompt；「我會給不同分數」代表信任問題要處理變革管理

隨堂測驗考點

Knowledge Checks
Knowledge Check 1
為什麼提案的 AI capability 一定要先對應痛點，而不能先選喜歡的技術？
✓

能力必須回溯到 Discover 階段診斷出的具體痛點；技術驅動或投機性提案一律被淘汰，絕不允許反向推導。

Knowledge Check 2
團隊沒有 AI 服務經驗、僅有 8 週試點時程，且採用 prove-ROI-first 預算模型時，build-buy-partner 決策該怎麼選？
✓

選擇 Blueprint（AWS PCA 參考架構）：從零建置時程不足且學習曲線太陡，採購商業方案則與預算模式及供應商依賴問題不合。

Knowledge Check 3
QA 需要未遮蔽逐字稿做教練，合規要求全面 PII 遮蔽，這種衝突該如何化解？
✓

用分層存取取代二選一：預設全面遮蔽，具名 QA 人員透過 Cognito 取得 72 小時到期的未遮蔽檢視，並全程稽核記錄——兩邊需求同時被滿足。

Knowledge Check 4
挑選摘要（summarization）模型時，判斷準則的優先順序是什麼？
✓

資料落地（residency）優先，維運複雜度次之：資料一旦離開 AWS 環境即淘汰（如 Anthropic API 直連），其餘選項再比較複雜度，Bedrock 兩項皆勝出。

Knowledge Check 5
四項 PCA 能力的風險等級是依據什麼判斷的？
✓

依能力產生「全新內容」的程度判斷：處理既有資料（轉錄、分類）風險低；產生新內容（摘要）風險最高，需要最多治理控制並延後部署階段。

Knowledge Check 6
QA 分析師的 AI 輸出覆寫率升高時，第一步該怎麼做？
✓

先追蹤覆寫的原因，而非只看覆寫率數字：「分數錯了」代表模型問題要修 prompt；「我會給不同分數」代表信任問題要處理變革管理。

⭐

一句話總結

治理與範圍要在設計階段就內建，用分層存取與具名角色化解利害衝突，讓 POC Scope Document 同時替工程團隊畫出邊界、替策略顧問訂出可驗證的成功標準。
